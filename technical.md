## ADR-001: JavaScript (JSX) вместо TypeScript

**Статус:** Accepted (требование пользователя)

**Решение:** Проект пишется на чистом JavaScript + JSX. Без TypeScript, без JSDoc-тайпинга.

**Обоснование:** Прямое требование пользователя. Снижает порог входа, ускоряет итерации.

**Альтернативы:** TypeScript — отвергнут требованием.

**Последствия / компенсация риска:**
- Нет статической проверки типов → риск опечаток в props/моделях.
- **Смягчение:** строгие контракты данных описаны в `specs/data-model.md` (JSDoc-комментарии
  с описанием формы объектов), именование по схеме, ESLint-правила. Любая функция,
  работающая с моделью данных, должна быть задокументирована формой входных/выходных данных.
- **Запрет (AGENTS.md):** не вводить TypeScript, не добавлять типы.

## ADR-002: SVG (hand-built) для рендера плана

**Статус:** Accepted

**Решение:** План этажа рендерится нативным SVG внутри React-компонентов. Геометрия комнат —
полигоны, объекты — группы элементов. Никакого Canvas, Konva, Three.js.

**Почему не Canvas:**
- Canvas требует ручного hit-testing для кликов по объектам; SVG даёт нативные DOM-события
  (`onClick`, `onMouseEnter`) на каждом элементе — критично для интерактива.
- SVG сохраняет идеальную чёткость линий при любом масштабе (зуме).
- Проще стилизовать (CSS/градиенты/фильтры), чем Canvas.

**Почему не Konva / react-konva:**
- Добавляет слой абстракции ради производительности на тысячах объектов — избыточно для плана
  этажа с десятками объектов.
- Хуже интегрируется с CSS-анимациями и SVG-фильтрами.

**Почему не Three.js / 3D:**
- Стиль Modern Minimal — плоский 2D с псевдо-объёмом через тени. 3D избыточен и ломает
  выбранный визуальный язык.

**Последствия:**
- Зум реализуется через трансформацию контейнера (см. ADR-005), а не через перерисовку
  геометрии.
- Производительность фильтров (`feGaussianBlur`) контролируется (см. ADR-006).

**Запрет (AGENTS.md):** не заменять SVG на Canvas/Konva без явного согласования.

## ADR-003: Управление состоянием — MobX (классовые сторы)

**Статус:** Accepted (требование пользователя)

**Решение:** Глобальное состояние — MobX 6. Сторы — классы с `makeAutoObservable(this)`.
Доступ в компонентах — через React Context (DI) и хук `useStore()`. Перерисовка компонентов —
через `observer` из `mobx-react-lite`.

**Структура сторов:**
- `RootStore` — собирает все сторы + ссылку на данные здания (`building.js`).
- `UiStore` — UI-состояние: `activeFloorId`, `visibleTypes` (Set), флаги UI.
- `SelectionStore` — `selectedObjectId`, методы `select(id)` / `clear()`.

**Почему классы, а не объекты с `observable`:**
- Классовый стиль — рекомендованный современный паттерн MobX 6 (`makeAutoObservable`).
- Удобно хранить действия (мутации) рядом с состоянием; `makeAutoObservable` автоматически
  делает поля observable, геттеры — computed, методы — action.

**Почему mobx-react-lite, а не mobx-react:**
- `mobx-react-lite` легче, предоставляет только `observer` и хуки — этого достаточно
  (legacy-провайдеры/`Provider` не нужны, используем React Context).

**Почему не Redux/Zustand/Context-only:**
- Redux — избыточен по шаблонному коду для масштаба задачи.
- Zustand — допустимая альтернатива, но пользователь явно выбрал **MobX**.
- Context-only без библиотеки — вызывает ре-рендер всех консьюмеров при любом изменении;
  MobX даёт точечные перерисовки.

**Правила (AGENTS.md):**
- Глобальное/разделяемое состояние — только в MobX-сторах.
- `useState` — только для локального UI-состояния одного компонента (например, open/close
  локальной менюшки, не затрагивающей остальные).
- В компонентах-наблюдателях читать из стора только то, что нужно компоненту (точечные
  подписки).

## ADR-004: Зум и панорамирование — react-zoom-pan-pinch

**Статус:** Accepted

**Решение:** Используем `react-zoom-pan-pinch` v4 (компонент `TransformWrapper` +
`TransformComponent`). Управление: колесо мыши, перетаскивание (pan), кнопки +/−/сброс
через `useControls`/методы императивного API.

**Почему готовая библиотека, а не собственная реализация:**
- Зум/пан с инерцией, ограничением границ, корректной точкой масштабирования под курсором —
  нетривиально; написание с нуля — риск багов и дёрганий.
- Библиотека зрелая, ~тысячи пользователей, поддерживает React 19.

**Почему не d3-zoom / own transform:**
- d3-zoom ориентирован на d3-экосистему, требует ручной интеграции с React.
- Собственный `transform` на SVG возможен, но теряем инерцию/ограничения «из коробки».

**Интеграция с SVG:**
- `TransformComponent` оборачивает `<svg>` (или контейнер с SVG). Трансформация применяется к
  контейнеру, сама геометрия SVG не пересчитывается → плавность.

## ADR-005: Поповер — @floating-ui/react

**Статус:** Accepted

**Решение:** Поповер с данными объекта позиционируется через `@floating-ui/react`
(преемник Popper.js). Якорь — выбранный объект (его экранные координаты).

**Почему floating-ui:**
- Умное позиционирование с переворотом (flip) и сдвигом (shift) — поповер не выходит за края.
- Поддержка виртуальных якорей (координаты точки), что подходит для объектов на плане.
- Лёгкая, без тяжёлых зависимостей, активно поддерживается.

**Почему не fixed-позиционирование вручную:**
- Ручной расчёт при зуме/пан/скролле хрупок; floating-ui решает это корректно.

**Координаты:** при выборе объекта его SVG-координаты конвертируются в экранные через
`getBoundingClientRect` элемента-якоря (или `DOMPoint`/`createSVGPoint` + `matrixTransform`).
Логика — в `utils/geometry.js`.

## ADR-006: Производительность SVG-фильтров

**Статус:** Accepted

**Решение:** SVG-фильтры (тени, свечение) объявляются **один раз** в `<defs>` и
переиспользуются по `id` через `filter="url(#id)"`. Запрещено плодить десятки инстансов
фильтров на каждый элемент.

**Обоснование:** `feGaussianBlur` и составные фильтры — дорогие операции. Повторное
определение на каждом элементе убивает производительность и качество при зуме.

**Правила:**
- Все фильтры — в едином `<defs>` корневого SVG плана.
- Имена `id` — по схеме `filter-<название>` (например, `filter-soft-shadow`).
- То же касается градиентов — в `<defs>`, переиспользование по ссылке.

## ADR-007: Стили — CSS Modules + CSS-переменные (тема)

**Статус:** Accepted

**Решение:**
- **CSS Modules** (`.module.css`) для изоляции стилей компонентов — Vite поддерживает из
  коробки.
- **Глобальные CSS-переменные** (`:root { --... }`) в `src/index.css` — единая дизайн-система
  (палитра, тени, скругления, тайминги анимаций).

**Почему не Tailwind / styled-components / CSS-in-JS:**
- Tailwind — допустим, но уводит от «дорогого» кастомного CSS, нужного для SVG-стилизации и
  тонких визуальных эффектов; для киллер-фичи удобнее рукописный CSS.
- CSS-in-JS (styled-components) — лишний рантайм; для SVG удобнее классы.
- CSS Modules дают изоляцию без рантайма и отлично дружат с SVG-классами.

**Инвариант (AGENTS.md):** глобальные CSS-переменные темы (`src/index.css`) и палитра
(`specs/design-system.md`) — не меняются без согласования.

## ADR-008: Данные — мок в `src/data/building.js`

**Статус:** Accepted

**Решение:** Данные этажей, комнат и объектов хранятся в виде JS-модуля-мока
(`building.js`). `RootStore` импортирует их и предоставляет компонентам. Контракты моделей —
в `specs/data-model.md`.

**Почему мок, а не бэкенд:**
- Первая итерация фокусируется на фронтенде и визуальном качестве.
- Мок позволяет быстро итерировать визуал без инфраструктуры.

**Последствия:**
- Архитектура (стор + модель данных) спроектирована так, чтобы замена мока на REST/GraphQL
  была минимальной: достаточно заменить источник данных в `RootStore`.

## ADR-009: Проектирование под расширяемость (Roadmap-ready)

**Статус:** Accepted

**Решение:** Архитектура закладывает точки расширения без преждевременной реализации:
- **Типы объектов** — enum-like в одном месте (`specs/data-model.md`), рендерер и фильтры
  управляются этим списком. Добавить новый тип — ограниченный набор правок.
- **Этажи** — список в данных, `UiStore.activeFloorId`. Добавление этажа = добавление записи.
- **Бэкенд** — изоляция источника данных в `RootStore` (см. ADR-008).

**Принцип:** YAGNI — не реализуем фичи из Roadmap сейчас, но не пишем код, который помешает
их добавить позже.

## ADR-010: Качество кода — ESLint (flat config) + Prettier

**Статус:** Accepted

**Решение:**
- **ESLint 10**, flat config (`eslint.config.js`). Пресеты: `@eslint/js` recommended,
  `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`.
- **Prettier 3.9** для форматирования. Конфиг `.prettierrc`: 2 пробела, двойные кавычки в
  JSX, одинарные в JS, без точек с запятой, trailing comma.

**Правила:**
- `npm run lint` должен проходить без ошибок перед завершением задачи.
- `npm run format` — для форматирования.
