# context.md — Контекст проекта

> Единый источник правды о том, **зачем** этот проект существует, какие **ограничения** на
> него наложены и что **нельзя ломать**. Читается ИИ-агентом перед началом любой задачи.

## 1. Цель проекта

Создать **продакшн-ready** веб-приложение для просмотра поэтажных планов здания с
интерактивными особыми объектами. Главная ценность — **красивая отрисовка плана этажа**:
это осознанный, заявленный пользовательелем фокус, а не побочный эффект.

Приложение должно выглядеть и ощущаться как **премиальный продукт**, а не как учебный
прототип.

## 2. Аудитория и сценарии использования

- **Демо/портфолио:** показать продакшн-подход к интерактивной векторной визуализации.
- **Основа для реального продукта:** внутренние системы безопасности/управления зданием,
  навигация по офису/ТЦ, дашборды.
- **Сценарий пользователя:** открыть этаж → найти нужный объект (лифт/камеру/банкомат) →
  кликнуть → посмотреть детали в поповере → при необходимости сменить этаж или отфильтровать
  типы.

## 3. Ключевое требование (киллер-фича)

> **Красота отрисовки плана этажа — высший приоритет.**

- Визуальное качество планa должно быть на уровне премиальных продуктовых UI.
- Выбранный стиль: **Modern Minimal** (светлый, воздушный, пастельные градиенты, мягкие тени,
  тонкие линии, аккуратная типографика).
- Любое изменение рендера плана обязано **сохранять или улучшать** визуальное качество.
- Деградация качества (плоские цвета без теней, рваные линии, отсутствие слоёв) — недопустима.

## 4. Зафиксированные решения пользователя (контракт)

Эти решения приняты пользователем и не подлежат пересмотру без явного согласования:

| Решение | Значение | Где зафиксировано |
|---|---|---|
| Язык/UI-фреймворк | **React + JavaScript** (JSX), без TypeScript | `technical.md` |
| Управление состоянием | **MobX** (классовые сторы, `makeAutoObservable`) | `technical.md` |
| Визуализация плана | **SVG** (hand-built, не Canvas/Konva) | `technical.md` |
| Стиль плана | **Modern Minimal** | `specs/design-system.md` |
| Типы особых объектов | **Лифты, Камеры, Банкоматы** | `specs/data-model.md` |

## 5. Критические инварианты («не ломать»)

1. **Стек:** React + JS (без TS). MobX для состояния. SVG для рендера плана.
2. **Палитра и дизайн-токены:** глобальные CSS-переменные темы (`src/index.css`) и палитра
   из `specs/design-system.md` — инвариант. Изменения только через согласование.
3. **Киллер-фича:** визуальное качество плана не должно деградировать.
4. **Зависимости:** только из списка в `technical.md`. Новые — с обоснованием и согласием.
5. **Документация:** спецификации (`specs/`) и зафиксированные решения (`technical.md`)
   актуальны и не удаляются без причины.

## 6. Границы (что НЕ входит в первую итерацию)

Первая итерация сфокусирована на **качестве плана одного этажа**. Вне scope:

- Реальный бэкенд (используем мок-данные в `src/data/building.js`).
- Импорт реальных планов (DXF/SVG) — план рисуется программно из полигонов.
- Роутинг/построение маршрутов.
- Авторизация, мультитенантность.
- Мобильные жесты (полноценно), мобильная адаптация (базовая — да).
- Тёмная тема (только светлая Modern Minimal).
- Тесты (e2e/unit) — закладывается архитектура под них, но сами тесты не в первой итерации,
  если не оговорено иное.

Эти пункты зафиксированы как **Roadmap** (см. `README.md`), к ним вернёмся позже.

## 7. Объём первой итерации (MVP scope)

MVP должен содержать:
1. Красивый SVG-план **одного этажа** (Modern Minimal, слоистый рендер).
2. **Зум/пан**: колесо мыши, перетаскивание, кнопки +/−/сброс.
3. **Особые объекты** на плане (лифты, камеры, банкоматы) с hover/selection-состояниями.
4. **Поповер** с детальными данными объекта при выборе.
5. **Переключатель этажей** (задел на 2–3 этажа, данные в моках).
6. **Фильтры** по типам объектов + **легенда**.
7. Реактивное состояние на **MobX**.

Детальный пошаговый план — в `plan.md`.

## 8. Допущения и риски

- **Производительность SVG-фильтров:** `feGaussianBlur`/`feDropShadow` могут быть тяжёлыми
  при большом количестве. Смягчение: фильтры в `<defs>`, переиспользование по ссылке,
  контроль числа инстансов (см. `technical.md`).
- **Производительность зума:** трансформация через CSS/SVG-атрибут `transform`, а не
  перерисовка геометрии.
- **Демо-данные:** геометрия придумана вручную, координаты подобраны для красивого вида.
  При замене на реальные данные контракты моделей должны сохраниться (`specs/data-model.md`).

## 9. Определение «готово» (Definition of Done)

Задача считается выполненной, когда:
- Код следует конвенциям `AGENTS.md`.
- `npm run lint` проходит без ошибок, `npm run build` собирается.
- Визуальное качество плана (если затронуто) сохранено/улучшено.
- Обновлена релевантная документация (`docs/`/`specs/`), если изменилось поведение.
- Нет отладочного кода (`console.log`, закомментированных фрагментов).
