# AGENTS.md — Инструкция для ИИ-агентов

> Этот файл читается ИИ-агентами (ZCode, Copilot, Cursor и др.) при работе с репозиторием.
> Он описывает соглашения проекта, запреты и обязательные правила, чтобы агент работал
> предсказуемо и не ломал продакшн-инварианты.

## 1. Контекст проекта

- **Что это:** Веб-приложение «Поэтажные планы здания» — интерактивный просмотрщик плана
  этажа с особыми объектами (лифты, камеры, банкоматы), зумом/панорамированием и поповером
  с данными объекта.
- **Стек:** Vite 8 + React 19 + JavaScript (JSX). MobX 6 для состояния.
- **Киллер-фича:** Красота отрисовки плана этажа (стиль Modern Minimal). Любые изменения
  рендера плана должны сохранять или улучшать визуальное качество — это высший приоритет.
- **Детали:** См. `context.md` (полный контекст), `technical.md` (технические решения),
  `plan.md` (детальный план), `specs/` (спецификации), `docs/` (пользовательская документация).

## 2. Что читать перед началом работы (обязательно)

Перед любой нетривиальной задачей агент **обязан** прочитать:

1. `context.md` — зачем проект, какие ограничения, что нельзя ломать.
2. `technical.md` — зафиксированные технические решения и их обоснование.
3. `specs/` — спецификации модулей, с которыми предстоит работать.
4. `plan.md` — текущий этап и статус (если вносит изменения в код).

Если спецификация или тех. решение противоречат требованию — **остановиться и спросить**
пользователя, не додумывать.

## 3. Правила работы с кодом

### 3.1. Обязательные практики
- **Читай существующий код перед изменениями.** Найди похожие паттерны (компонент, стиль,
  мобиксовый стор) и следуй им. Код должен читаться так, будто его написал тот же автор.
- **Следуй именованию.** Компоненты — PascalCase, хуки/утилиты — camelCase, файлы
  компонентов — PascalCase, всё остальное — kebab/camel по существующей конвенции.
- **MobX:** все сторы — классы с `makeAutoObservable`. Действия (мутации) — методы стора.
  В компонентах — `observer` из `mobx-react-lite`, доступ через `useStore()`. Не используй
  `useState` для глобального/разделяемого состояния.
- **Сторонние пакеты — только из `technical.md`.** Если нужен новый пакет — спроси
  разрешение и обоснуй. Не тяни тяжёлые зависимости без необходимости.
- **Комментарии — на русском** (как существующий код), в редких случаях на английском для
  общеупотребительных терминов. Пиши комментарии только когда они добавляют ценность.

### 3.2. Запреты (критичные инварианты)
- ❌ **Не используй TypeScript** — проект на чистом JavaScript (JSX). Это сознательное
  решение (см. `technical.md`).
- ❌ **Не заменяй SVG на Canvas** для рендера плана. SVG выбран сознательно (см.
  `technical.md` §«Почему SVG»). Canvas/Konva — только если явно докажешь необходимость.
- ❌ **Не меняй глобальные CSS-переменные темы** (`src/index.css`), не сверившись с
  дизайн-системой в `specs/design-system.md`. Палитра — инвариант.
- ❌ **Не добавляй `!important`** в CSS без крайней необходимости и без комментария-причины.
- ❌ **Не коммить** без явного разрешения пользователя. Не пушь без спроса.
- ❌ **Не удаляй и не переписывай спецификации/документацию**, если задача не про это.
- ❌ **Не используй `any`-подобные костыли** и не обходи ошибки — разбирайся в причине.

### 3.3. Производительность
- MobX-компоненты (через `observer`) перерисовываются точечно. Не делай лишних подписок —
  читай из стора только то, что нужно компоненту.
- SVG-план: тяжёлые фильтры (`feGaussianBlur`) — в `<defs>`, переиспользуются по ссылке.
  Не плодить десятки инстансов фильтров.
- `React.memo` — только там, где доказано измерением, что это нужно.

## 4. Стиль и качество кода

- **Линтинг:** ESLint (flat config) + Prettier. Конфиги уже в репозитории. Перед завершением
  задачи запускай `npm run lint` — должен быть 0 ошибок.
- **Форматирование:** 2 пробела, двойные кавычки в JSX, одинарные в JS, без точек с запятой
  (см. `.editorconfig`, `.prettierrc`).
- **Не оставляй закомментированный код**, `console.log`, отладочные артефакты.
- **Имена должны отражать смысл:** `selectedObjectId`, а не `id2`.

## 5. Структура и архитектура (что где лежит)

```
src/
├─ main.jsx               # Точка входа, провайдер RootStore
├─ App.jsx                # Корневой layout
├─ index.css              # Глобальная тема (CSS-переменные) — НЕ ТРОГАТЬ без согласования
├─ data/building.js       # Мок-данные (этажи, комнаты, объекты)
├─ state/                 # MobX-сторы (классы)
├─ components/
│  ├─ FloorPlan/          # Слоистый SVG-рендер плана (КИЛЛЕР-ФИЧА)
│  ├─ Controls/           # Зум, этажи, фильтры
│  ├─ ObjectPopover.jsx   # Поповер (@floating-ui/react)
│  └─ Legend.jsx
└─ utils/                 # Чистые функции (геометрия и др.)
```

Подробное описание модулей и их контрактов — в `specs/`.

## 6. Workflow для задачи

1. Прочитай релевантные разделы `context.md`, `technical.md`, `specs/`.
2. Если в `plan.md` есть статус — сверься, на каком этапе работа.
3. Пиши код малыми шагами, проверяй после каждого (`npm run dev`, `npm run lint`).
4. Перед завершением: `npm run lint` чист, `npm run build` проходит.
5. Обнови документацию (`docs/`, `specs/`), если поменялось поведение.
6. Кратко отчитайся: что сделал, что проверил, что осталось.

## 7. Когда спрашивать пользователя

Спрашивай, когда:
- Требование противоречит зафиксированному решению в `technical.md`.
- Нужно добавить новую зависимость.
- Есть развилка в дизайне/архитектуре с несколькими равнозначными вариантами.
- Изменение затрагивает критичный инвариант (палитра, SVG-рендер, стек).

Не спрашивай очевидного — выбирай разумный default, сообщай о выборе.
